## Recommendation and evidence boundary

Introduce one neutral `ClosedCatalogTransferOrchestrator` in `Lightflow.Application`, coordinating existing lifecycle, mutation, recovery/snapshot, configuration and platform operations through narrow ports. Names/signatures are proposals. Retain concrete SQLite services in their current owner until an authorized extraction is necessary. Do not create a Catalog manager, another backup engine, identity validator or writer. Settings and a future Mac host consume the same orchestration and lifecycle transaction.

Separate four roles: local active Catalog, closed Catalog transport, verified backup destination, and media. Active network Catalogs remain refused; network media remains allowed; network backups use local finalized snapshots and verified byte transport. ExFAT remains refused for active production Catalogs. Suitability always comes from shared `StorageLocationPolicy`, with fresh native facts, never from transfer code's filesystem name heuristics.

Accepted #388/#401, #389/#403 and #390/#404 are completed/merged; #403 merged as the baseline above. #272 is completed. #406/#407 is accepted **bounded research**, with product qualification outstanding. #391 is actively owned by LF-WIN-DEV-009 (Project In Progress and owner kickoff), although its original issue body still says unstarted. This review neither changes that implementation nor assumes an unaccepted API. Assignment 010 is unused on baseline main; owner explicitly allocated it in this kickoff. Concurrent registry reconciliation must preserve 009 and Agent 005's completion publication.

G2's accepted P2 evidence demonstrates local NTFS → closed archive through NAS → local APFS → closed return → NTFS, preserving 23-table authored state and stable IDs, within synthetic/production-linked fixture limits. It retains the direct WAL-to-SMB journal-finalization CANTOPEN14 failure. #406's physical fixture preserved 24 Mac and 14 Windows hashes, Catalog/Root/32 AssetIds and one intended note delta; Mac/Windows phases were CONDITIONAL, immutable Mac return PASS. macOS ExFAT `renameatx_np(RENAME_EXCL)` returned errno 45; verified exclusive copy succeeded without proving atomicity. Neither proof qualifies complete production Settings/lifecycle, unexpected removal, atomic publication or power-loss durability.

**No common external active-Catalog filesystem is currently qualified by both accepted adapters.** Windows admission uses qualified NTFS; Mac qualification is bounded internal case-insensitive APFS, with external qualification unknown. The required direct external Windows/Mac workflow is therefore a product gate, not a capability this design can declare delivered. Validate shared engine/local-platform legs independently; #406 and accepted support evidence must resolve the physical interchange gate. Do not require third-party filesystem drivers or silently enable ExFAT.

## Closed artifact and neutral ports

Proposed ports to the existing owners: finalize/validate a local snapshot; hold/drain/close/reopen an existing lifecycle session; stage/stream/hash/read-back/flush/publish through platform file operations; assess via existing assessor/policy; consume #391 identity report; reversible activation and configuration commit. These are capabilities of existing owners, not independently instantiable writer engines. Neutral code contains no SQLite/native/WPF types.

Each operation has a new OperationId and generation, mode (MoveAndActivate / ClosedTransport / BackupTransport / LocalCopyback), expected CatalogId/schema, source snapshot identity and destination intent. Bind machine-local resolved object, parent, volume/mount epoch and filesystem facts separately from durable CatalogId. Tokens are operation-scoped and not portable mount identifiers. Persist no handles as authority; restart requires new assessments and object verification.

Versioned manifest: OperationId, format/version, CatalogId, source schema/application identity, snapshot UTC, declared artifact roles, exact safe relative names, byte sizes, SHA-256 per file and canonical manifest digest, snapshot validation receipts/provenance, publication mode and readiness record version. No absolute machine paths as portable identity. Reject traversal, duplicate/colliding names, unexpected files, links, missing required artifacts and unrecognized required roles. Hash binds bytes, not permission, authenticity against an adversary, writer ownership or filesystem durability.

For **move**: standalone local finalized `LightflowCatalog.db`; all recognized managed `Backups` DBs and their metadata present at the boundary, inventoried and hashed under the existing recovery owner, without applying retention as part of move. Validate their identities and classify nonmatching/unusable historical evidence explicitly; do not discard evidence or silently present it as verified. Unknown precious files or unsafe links block the move pending review. Preserve stale startup evidence only at source; destination starts deep validation. Profile-owned user backups outside CatalogDirectory stay at their configured location and are not silently relocated. Snapshot **backup** mode carries only the validated DB and required transfer manifest/readiness data, plus existing supplementary metadata; it is not a recursive copy of historical backups. LUT content references require existing managed-LUT dependency validation: do not claim DB alone transfers externally stored LUT bytes; scope for any required durable dependency must be reviewed before implementation.

Snapshot owner proves SQLite consistency: accepted-operation drain (for move/exit boundary), finish accepted SQL work, close/drain read consumers for move, finalize SQLite backup locally into operation-owned storage with standalone journal mode, dispose its connections, prove no required WAL/SHM/journal remains, validate identity/schema/full integrity, flush and hash closed bytes. Never manually discard a source WAL. Source may retain SQLite-managed companions until its lifecycle closes them. Backup may keep active source lifecycle while transporting an immutable output; move keeps source authoring closed until commit or rollback. Owner must establish exclusive closed-source use; app instance/pool closure alone does not prove another process cannot reopen it.

## Durable state machine and retry

Local profile owns an append-only/versioned operation journal outside CatalogDirectory/Preview/temporary purge roots. Record validated old/new config values, source/destination binding evidence and artifact identities, manifest digest, state intent/completion, activation/config transaction receipt and recovery disposition. Store journal with existing durable profile file operations, not a Catalog schema. Required journal/marker writes are flushed with truthful capability receipts. Partial/truncated/out-of-order records yield RecoveryRequired; no timestamp/path-only inference of success. Journal supplies evidence, never path authority.

| State | Required effect before completed record | Restart / safe retry |
| --- | --- | --- |
| Preflight | Assess source and destination roles, identity, space including snapshot/staging, protected containment and collisions; capture prior config. | No writes to selected Catalog; new facts for retry. |
| Quiescing | Existing lifecycle rejects new authoring, drains admitted mutations then relevant reads/background consumers. | Resume prior lifecycle if safely bound; never resume old admitted work from journal. |
| SnapshotFinalized | Existing recovery owner creates, closes, validates, hashes local immutable manifest set. | Reuse only if entire set and identity reverified; otherwise make new snapshot/operation. |
| Staging | Exclusive operation-owned container + persistent pending record created **before** payload writes. | Incomplete/unlisted; restart full copy simplest. Resume chunks only after independent hashes/binding, not size alone. |
| Verified | All closed payload sizes/hashes read back, manifest validated; schema/integrity/identity checks on suitable local bytes and #391 report match. | Reverify current objects and readiness after reconnect; never borrow old mount epoch approval. |
| Published | Capability-selected commit below; re-read complete record and all artifacts before publication receipt. | Published transport is not active. Unknown receipt remains recovery-required. |
| Activating (move only) | Existing lifecycle opens intended local destination under fresh active admission, protects any allowed migration, checks selected identity, binds consumers reversibly **with authoring still blocked**. | Neither source nor destination opens writable normally until journal/config resolved. |
| ActivatedPendingConfiguration | Lifecycle verifies destination activation/one-owner result; previous config still durable. | Close provisional destination and recover prior config/source unless commit can be established. No new authored state accepted yet. |
| ConfigurationCommitted | Existing config owner saves/reloads destination path+CatalogId after activation. Record matching receipt, then release user authoring. | Matching journal/config/destination → ordinary deep open. Incomplete receipt → revalidate/recover, not create. |
| Completed | Requested mode result durable; move has activated+saved; transport has verified publication; release operation handles/anchors. | No automatic source deletion. Once destination authoring admitted, cannot silently roll back to stale retained source. |
| Cancelled / Failed / RecoveryRequired | Stop at safe boundary; rollback existing lifecycle/config if proven; otherwise disable writer, retain all evidence. | Explicit reconnect/review/new preflight; never delete by remembered spelling. |

Write intent before every externally visible irreversible boundary and completion after verifying effect. ConfigurationCommitted is the logical switch commit, **not** a cross-volume atomic transaction. Activation before save is reversible and read-blocked/user-authoring-blocked; no destination edits may be acknowledged in that interval. Lifecycle may perform its normal protected migration on the destination, so hash receipts describe the transferred pre-open snapshot; lifecycle receipts separately describe the post-open schema. Do not compare migrated bytes to old snapshot hash or downgrade schema. For moves within the same current build require expected schema equality; existing older-Catalog opening uses existing protected migration policy. Recovery on restart checks pending journal before normal configured startup, even if config points at source.

Cancellation is accepted during preflight/drain/copy/hash at supported boundaries. SQLite backup/native calls may finish before cancellation can be observed; no thread abortion. Before publication/activation/config commit, finish a short noncancellable commit-or-rollback interval and report its actual result. UI can show “Finishing safely…” and stop accepting Cancel at that boundary. If cancellation arrives after committed activation, show completed outcome, not pretend rollback. Normal authoring resumes on verified source rollback only. No journal recovery silently chooses between two independently edited same-ID copies.

## Publication and platform responsibility

Storage suitability and publication capabilities are separate. #388 facts do not currently prove no-replace rename, atomic replacement or directory-entry durability. Proposed narrow file-operation results must report actual exclusive creation, atomic publication when qualified, required file/directory synchronization acknowledgement and readback. Unknown/unsupported operations choose conservative transport fallback or refuse activation; never set eligibility from publication capability.

| Location | Evidence / allowed design |
| --- | --- |
| NTFS qualified local | Existing Windows accepted app admission and SQLite behavior. Qualify same-volume no-replace publication/recovery separately; current File.Move use is not evidence for all compound artifacts or power loss. Retain source; never overwrite unrelated destination. |
| Internal case-insensitive APFS | Accepted Mac facts and G2 local SQLite. Qualify native exclusive publication + directory sync + marker readers, object-bound use and teardown; assessment success alone grants none. |
| ExFAT | Physical closed fixture copy/hash succeeded; Mac exclusive rename unsupported (errno 45). Use transport container fallback only; active production admission stays refused regardless of copied bytes. |
| Other/local external | Local connectivity is not qualification. Existing policy's unknown capability refuses active use; closed transport requires verified staging and effect-level capabilities. |
| Network backup | No SQLite open there. Unique staged transport container, readback hash and completion-gated discovery; no universal network rename/flush guarantee. Keep prior verified backups. |

**Qualified atomic mode:** build verified complete set in a unique same-volume staging directory; no-replace publish into an unused final directory if adapter and readers support the operation. Catalog unit includes Backups, so a single DB rename alone does not atomically publish the set. Where selected destination directory must already exist, use an operation-owned child and explicitly define resulting Catalog directory in confirmation, or refuse that mode; do not replace an existing user's directory. Qualify exact host selection/layout before implementation. Revalidate containing object and intended target at publication/use; don't unlink a collision. Flush files and required directory entries through qualified adapter. All validation/discovery still checks pending/readiness, no bypass from atomic mode.

**Conservative copy mode:** leave payload exclusively inside a uniquely created `*.incomplete` transport container with nonstandard payload filename (`catalog.snapshot`), required pending/readiness protocol and manifest. Copy with exclusive creation, read back every byte hash, close writers, then exclusively write a bounded complete record binding manifest digest, count and identities. A torn/missing record or missing/mismatched payload is incomplete. Readers require valid full record **and** complete manifest verification; a marker alone is never success. Directory need not be renamed. Do not expose `LightflowCatalog.db` or legacy `LightflowCatalog-User-*.db` while copying. Newly supported backup listing resolves containers only through this validator; current glob listing must change. Legacy plain DB backups remain readable via existing local-copyback/full validation, not automatically blessed by a new marker.

Copy-mode publication is **logical readiness**, not crash-atomic publication. A validated complete container remains a transport artifact and cannot be selected as an active Catalog. Copyback stages it on a qualified local filesystem for separately validated lifecycle installation. If active destination cannot provide a qualified final publication/reader protocol, refuse activation. This avoids exposing a partial standard-name Catalog to older applications that ignore new markers. New marker-based Catalog layouts or minimum-reader compatibility would require explicit design acceptance; this review does not silently change layout or authorize older clients to open incomplete containers.

Exclusive creation prevents overwriting but does not make a multi-file copy atomic. Atomic replacement changes a namespace entry but is unnecessary for moves to empty locations and must not destroy previous verified backup. Hash verification detects byte mismatch at observation time, not later loss or tampering. Flush/fsync acknowledgement describes OS/storage-stack acceptance, not controller honesty or hardware power-loss proof. No success claim for unsupported sync semantics; publication may be left unverified with actionable result. Preserve verified prior destination versions; new backups use unique names, no “latest” overwrite/retention change.

Revalidation must bracket actual object-bound reads/writes/publication/cleanup. Source/destination tokens lose authority on alias/volume change; native handles/anchors scope to operation and release before eject. A new mount at the same spelling is not the old volume. Restart can re-establish a binding by explicit selection, full identity/manifest checks and fresh ownership; never replay deletion from stored paths. Cleanup whitelists only operation-created artifacts whose parent/object identity is freshly proven. Refused cleanup leaves quarantined evidence, not an error hidden by broad finally-delete.

## Network backup and restore transport

`BackupForExitAsync` keeps its existing drain/exit-quiescence semantics. Recovery service snapshots to task/profile-owned **local** staging, full-validates once at the snapshot boundary and finalizes it. Transport orchestrator streams closed files to network staging, verifies readback size/hash, publishes by capability, and reports only a verified completed backup. No source/destination SQLite connection is created on NAS. No schedule, optimization, hidden shutdown backup or user-copy retention change.

Validate backup role conditional suitability before actual writes and revalidate bindings at boundaries. Disconnection/cancel/hash mismatch leaves incomplete/unlisted output, prior verified copies retained and live Catalog/config intact. The local finalized snapshot may be retained for explicit retry with full revalidation; no unbounded automatic retry or successful-exit signal. Existing dialog offers retry/change destination/skip/remain and keeps the app alive until safe terminal state. Exit skip/disabled stays fast.

Restore reads the complete manifest, streams to operation-owned local staging, independently hashes locally, validates source Catalog identity/supported schema/full integrity via recovery owner, then uses `RestoreCatalogAsync`/`BeginRestoreValidatedAsync` with local ActiveCatalog RestoreActivation admission and protected rollback. Never let network suitability stand in for local activation. Restore-over-current retains existing same-Catalog identity rule; adopting another valid Catalog uses explicit Open Existing instead. Existing pre-restore protection and managed retention remain unchanged. Avoid redundant full scans only when a receipt remains bound to unchanged local bytes; hashing transport does not replace the required SQLite validation boundary.

Expose in Settings' Catalog section **and** existing missing/unavailable Catalog recovery/setup surface. Select containing directory with `LightflowCatalog.db`; refuse missing selection without CreateNew. Receiving-machine first launch must offer this before automatic default initialization. ## Cross-platform mapping consumption

Use #391's accepted shared validator and native facts, not guessed drive-letter substitution. CatalogId/RootId/AssetId belong to existing repositories. Windows `D:\Media` versus macOS `/Volumes/Drive/Media` are per-machine locations for the **same reviewed RootId**, not new roots. Relative asset paths remain authored/persisted unchanged. Transfer is not permitted to normalize case/Unicode, trim names or reinterpret backslashes as a historical-key migration.

If another machine lacks a mapping, show missing/offline media and offer explicit existing RootId mapping after validator review. Network media remains eligible under MediaSource role; external media remains separate from active Catalog locality. Root mapping requires current native target checks, no overlaps/duplicate ambiguous candidates, and collision corpus acceptance. Case/Unicode/name/backslash ambiguity blocks affected unsafe authoring/transfer admission as #391 specifies, without deleting or rewriting rows. Reconnection at changed mount requires fresh review/preflight. No automatic fingerprint-based relinking or rewriting old machine mappings. Catalog opening must not trigger auto-discovery creating duplicate roots/assets before mapping safety is established.

## Failure and recovery matrix

In every row source and prior verified destination are retained. Cleanup always requires renewed object/parent ownership; otherwise quarantine. Evidence codes correspond to the acceptance suite below; these are required tests, not executed results.

| Rollback failed | RecoveryRequired / L,R,P | No safe active Catalog; name retained source/candidate and recovery action | Retain both; no success warning | Source reopening/config restoration faults; unavailable state and no double writer |
| Previous verified backup exists | Current attempt fails / R,T | Prior backup still available | Never overwrite/delete prior verified version | Hash prior backup before/after new publication failure |
| Incomplete staging found at restart | RecoveryRequired / T,L | Interrupted operation isolated | Never glob as backup/Catalog | Torn/missing readiness, malformed manifest, unknown version, orphan container |

After Completed and new edits, rollback to old source is a separate explicit recovery choice with stale-copy warning. A matching CatalogId alone cannot distinguish independently edited copies; no merge or best-time-wins selection. If configuration committed but journal final append failed, block new authoring until config/destination activation receipt can be reconciled; don't return success without durable completion evidence. Preserve any accepted destination edits rather than automatically opening stale source on next launch.
