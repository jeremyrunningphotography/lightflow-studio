## Native facts and qualification

Open the existing directory or nearest accessible creation ancestor with Win32 `CreateFileW`, without creating anything. A missing intended leaf is bound to its accessible ancestor plus the exact intended relative suffix. `GetFinalPathNameByHandleW` resolves the actual target. A volume-GUID path plus `GetDriveTypeW` establishes local Fixed/Removable versus remote UNC; a local-looking alias or mapped drive cannot qualify merely from spelling. Fixed and Removable receive identical qualification rules. Unavailable and unresolved observations fail closed.

`GetVolumeInformationByHandleW` identifies the filesystem instance, serial and native flags; `GetFileInformationByHandle` establishes directory/file identity. Accepted [G2 P2 evidence](../research/mac-catalog-proof/local-portability/P2_FINAL_RECOMMENDATION.md) qualifies local Windows NTFS. This implementation additionally requires a native disk handle and persistent-ACL/Unicode capability flags. NTFS naming alone is insufficient. Other filesystem types are unsupported; incomplete native evidence is Unknown. Local NTFS's supported Windows file locking, flush/durable-write API semantics and companion-file behavior are the qualified logical profile. This does not certify controllers, physical caches, power loss, surprise removal or physical portable-exFAT use. USB/Thunderbolt does not expand filesystem qualification; an NTFS external local volume is eligible on the same facts as an internal one.

OS references: [resolved handle paths](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew), [volume information by handle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumeinformationbyhandlew), [CreateFile directory/sharing semantics](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [file information classes](https://learn.microsoft.com/en-us/windows/win32/api/minwinbase/ne-minwinbase-file_info_by_handle_class), [file buffering/durability](https://learn.microsoft.com/en-us/windows/win32/fileio/file-buffering), [file locking](https://learn.microsoft.com/en-us/windows/win32/fileio/locking-and-unlocking-byte-ranges-in-files).

Read/write access is checked by non-creating opens for directory list/add-file/add-directory rights and existing database read/write rights. Read-only volume flags reject writes independently. Catalog database/SQLite companions may not be directories, reparse leaves or multiply linked files. Native resolved Catalog/Preview/Temporary containment must be non-overlapping. An unsupported reparse tag is Unknown, not a supported alias.

## Operation lifetime and failure safety

Each native assessor belongs to one operation and is disposed after it. The mount identity combines a fresh operation epoch with native volume-GUID/serial identity, bound to retained directory handles; it is not a persistent machine or Catalog identity. Directory read handles exclude delete/rename. Known junction/symlink objects additionally exclude write-based retargeting; both spelled and resolved ancestry are pinned. Metadata-only access-zero handles would not enforce sharing exclusion and are deliberately not used for these pins.

Every boundary checks the original retained handle and a freshly opened spelling/target, then supplies a fresh AssessmentId/time to shared Revalidate. Invalidated handles, replaced mounts, changed aliases, changed facts, cancellation and reused snapshots stop admission. Newly created intended directories are checked against the original resolved parent/suffix; creation does not silently substitute a different target. Expiry is only an upper bound and never replaces a native boundary probe. Handles and checks protect ordinary filesystem transitions; this is not a hostile-process/security sandbox or physical-removal certification.

Final SQLite access, migration safety copies, relocation staging/finalization and restore installation use the assessed volume-GUID path. A drive-letter substitution between probe and use therefore cannot redirect these operations. This is operation-only canonical routing to the same native target; configured locations and the session's public display path remain original. SQLite connections retain the resolved path after activation. Isolated-profile checks still validate the original requested database path before every native admission probe; the operation retains its checked ancestors/target rather than turning an arbitrary device path into a new profile. Startup Catalog evidence is read/written against the same bound database. No canonical path is persisted as a replacement storage choice.

Assessment precedes Catalog startup certificates and SQLite use. Refusal does not save settings, migrate/open the database, create an empty fallback or change IDs. Existing Preview and independent functionality can remain available through the existing unavailable-Catalog coordinator. Late refusal disposes any pending session and preserves the configured target; cleanup cannot follow a revoked binding. Relocation preserves its source, and rollback reopens only after fresh source admission. A configuration rollback failure during admission refusal cannot activate a destination writer.

Diagnostics distinguish unavailable storage, read-only access, unsupported filesystem and incomplete/ambiguous facts. Network refusal explains that active Catalogs require supported local drives while media and closed backups may use network locations. Existing MainWindow/Settings unavailable-Catalog presentation carries the diagnostic; no new dialog/setup workflow or UI styling is introduced.
