## Decision

Retain full native directory, volume, protected-root and Catalog-leaf assessment, but have the existing SQLite owner establish a **closed SQLite boundary before repeated full leaf assessment during unpublished startup/migration/activation**. Keep bound-location revalidation coupled to every existing identity-sensitive use. Do not replace post-open leaf assessment with an assertion that SQLite owns safe companions.

The assessor is currently observing SQLite-managed files without coordination with their lifecycle. That is a real ownership mismatch. However, SQLite ownership of their contents does not prove that a later pathname cannot resolve to an unsafe leaf. Directory pins do not pin child files, and the current Catalog session does not retain a continuously open SQLite connection. Dropping companion checks therefore lacks equivalent protection.

The selected correction is a constrained version of option A (coordination, no permissive retry). Preserve all rejection predicates. At a safe unpublished boundary, dispose all operation-owned connections/readers/transactions, clear only that Catalog factory's idle pool, then perform a fresh full assessment. Preserve the main database object across pool closure with an operation-owned native read handle that permits SQLite reads/writes but excludes delete/rename. Do not pin WAL/SHM/journal against SQLite deletion. Add precise containment-predicate diagnostics. A denial or ambiguity that remains at the closed boundary still refuses use.

This is a defensible safety-preserving correction strategy, **not a demonstrated root-cause fix**. Native handle compatibility and the bounded performance cost must pass the regression contract. If the exact refusals persist, retain their evidence and STOP; do not grow this into another investigation or weaken the checks.

## SQLite companion and replacement safety

The main DB carries durable identity/schema/data. WAL may contain committed data not yet checkpointed into the DB; it cannot be discarded or raw-copied in isolation. SHM is SQLite's rebuildable WAL coordination index, but an unsafe SHM target is still an unsafe file write/mapping. A rollback journal can contain crash-recovery information, including during an existing database's initial inspection; it must not be deleted merely because the selected runtime uses WAL. [SQLite WAL lifecycle](https://sqlite.org/wal.html) and [temporary-file roles](https://sqlite.org/tempfiles.html) support these distinctions.

SQLite may remove/recreate companions as connections close/open. A disposed managed pooled connection does not establish closed native handles; [Microsoft pooling documentation](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/connection-strings) and the factory/session source require explicit owner coordination. Neither a checkpoint nor mutation drain alone proves that readers and pooled handles are gone. Windows [CreateFile sharing rules](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) also require distinguishing access-zero metadata handles from read handles that actually exclude delete/rename.

Before any fresh SQLite access: independently establish local qualification, access, directory/volume/alias binding, protected-root non-overlap and safe named main/companion leaves. SQLite then owns bytes, consistency, locks, journal recovery and runtime-policy verification. Native binding and namespace safety remain native facts. Under this recommendation no post-use leaf fact is simply delegated or cached as success.

| Risk | Required protection / failure behavior |
| --- | --- |
| Pre-open sidecar symlink/reparse/directory/hard link | Full native leaf rejection before SQLite can follow/use it; target bytes untouched. Multi-link leaf remains rejected; no special SHM exemption. |
| Post-open attempted sidecar substitution | Do not hold sidecars against legitimate delete/recreation. If replacement succeeds during a deliberate test pause between closed boundary and next assessment, next full assessment rejects before next SQLite use/activation. If OS blocks it, verify original operation remains safe. A raced hostile replacement after the final snapshot is not solved by current admission either; never claim security-sandbox protection. |
| Main DB replacement | Pool closure can remove SQLite's own no-delete protection. Retain a native no-follow main-file read pin over that gap; record object identity and compare at boundary. Pin fails or identity changes: refuse. Authorized closed restore must release/rebind it explicitly, not silently accept another object. |
| Junction or drive-letter substitution | Existing spelled/resolved ancestor pins, fresh original-spelling comparison and volume-GUID use remain. Changed alias after activation still refuses restore/relocation before closing writer. |
| Mount replacement or active-directory move/delete | Existing retained-handle/fresh-target checks reject or native pins prevent operation during admission. Pins are operation-lived; active session routes to bound path. New operation requalifies. Physical removal is not certified. |
| Legitimate SQLite deletion/recreation | Allow SQLite to close/delete normally before full leaf snapshot. Missing companion retains existing 2/3 handling; existing safe single-linked regular companions are permitted. Zero links and denial are not translated into safe facts. |
| Concurrent connections / process | Unpublished service owns the applicable connections. Do not clear pools under published active readers/writers. Existing single-instance/mutation owners remain. No new mutex or writer model; unsupported competing writers are not made supported. |
| Unexpected partial migration | Step transactions/history/user_version, mandatory existing-Catalog backup and unchanged failure handling preserve recoverable committed steps. Refusal never triggers an empty replacement or destructive cleanup of a revoked target. |

Native main pin is an admission identity guard, not a SQLite writer lock or a new locking model. It must share normal reads/writes and must not retain WAL/SHM/journal handles. It lives only across the unpublished qualification/migration/activation interval. On ordinary authorized cleanup, close SQLite, revalidate binding, release the main pin, then perform only existing operation-owned cleanup. On admission revocation preserve artifacts and release pins without path deletion. Successful activation releases operation pins after the final required assessment; no new permanent session guard is implied.

## Containment diagnosis

At this head `AmbiguousContainment` can be produced by only three explicit predicate sites: resolved Catalog/protected-root `PathsOverlap`, leaf attributes containing Directory/ReparsePoint, or leaf handle `Links != 1`. These are different safety claims collapsed into one fact. API/access failures take the outer catch and yield Unknown facts, not that explicit ambiguous flag. Thus a temporary native denial alone does not directly explain Failure A.

Missing protected roots resolve to accessible parent plus intended suffix and are not inherently ambiguous. Legitimate partial directory creation similarly is not overlap by itself. Alias changes, inaccessible ancestry or changed directory binding generally throw, causing fail-closed unknown observations. An inconsistent snapshot can arise between attributes/open/link-count calls or while protected roots become real directories; a genuine alias/overlap remains possible. Normal SQLite deletion could affect leaf metadata, but the exact production-API observation in Failure A is unknown.

Every predicate setting Ambiguous must retain: discriminator (`ProtectedRootOverlap`, `LeafDirectory`, `LeafReparse`, `LeafLinkCount`), protected role or leaf name, requested/canonical target hash+length, handle file identity, attributes/link count, API name, observation ordinal/time, admission phase/operation/generation/assessment IDs. For exceptions retain numeric code and exact operation arguments. Diagnose all contributing predicates, not just the last one. Never dump owner paths or database content into CI evidence.

Closed-boundary diagnostics must additionally show which factory was closed, no operation-owned connection/reader/transaction remains, pool-clear completion, retained main identity and fresh target comparison. This distinguishes legitimate companion churn from overlap, unsafe aliases and unknown access. Do not infer missing evidence from a later passing run.
