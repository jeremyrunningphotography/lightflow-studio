# #340: Preview accounting implementation and integrity-policy decision

Status: census implementation authorized; integrity-policy proposal below is NOT approved or implemented. Baseline: main 202f15ec771b6452150b9c06710bc9727989009d. No changes to schema, retry state, migration, recovery, backup, or integrity checks.

## Implemented census contract

`MainWindow.Loaded` previously called `RefreshPreviewUsageAsync`, which reached `StorageManagementService.GetPreviewUsageAsync` and `PreviewMaintenanceService.GetUsageAsync`. Its purpose was the Settings storage-use label: database/cache byte totals, record/file counts, and orphan count. `ListAsync` read all Preview payloads and constructed every PreviewRecord; `Measure` additionally collected files and reference paths. This was unsolicited post-presentation accounting, not a readiness/safety requirement.

Startup no longer requests that accounting. Settings retains its existing Refresh Usage action, also used after explicit maintenance/relocation. It executes one `SELECT COUNT(*) FROM PreviewRecords;` through the existing initialized, serialized store, then streams cache files to sum their actual sizes and count artifacts. File enumeration is for file sizes and artifact totals, never to infer database record count. No file array, reference hash set, domain dates, metadata JSON, or PreviewRecords are loaded for usage. File I/O remains proportional to cache files on explicit refresh; this change does not make disk accounting constant-time. Byte totals across SQLite/files are informational, not an atomic cross-filesystem snapshot.

Orphan count is explicitly unknown for ordinary usage. Exact orphan reconciliation remains part of explicit Cleanup, whose behavior is unchanged. The Settings hint explains this. `RecordCount` is now a 64-bit scalar; `OrphanCount` is nullable rather than claiming an unmeasured zero.

Accepted old evidence: 2,121,692 PreviewRecords materialized, roughly 30 seconds post-presentation, approximately 5.4 GB process peak. New startup: zero usage queries and zero usage PreviewRecords. Explicit usage: one aggregate query, one scalar result, zero PreviewRecords. COUNT still reads SQLite pages; it is not promised O(1).

Deterministic coverage uses 20,000 SQLite-valid rows with 1,024-byte metadata payloads and deliberately unparseable domain dates. Production CountAsync succeeds without domain projection; native SQLite tracing verifies one COUNT statement and one result. Persisted failure values, schema, and database health remain unchanged. A separate service fake returns the production-scale count and throws on ListAsync, proving the usage service cannot enumerate records. Existing startup source-contract coverage forbids usage calls from Loaded. Byte/file totals and cancellation have focused coverage.

Targeted read-only production-copy probe: count 2,121,692; one COUNT statement; one aggregate result; 1,520 managed allocated bytes; 33,902,592-byte probe-process peak; 38.7 ms in that already available copy. Five additional native row callbacks belonged to internal schema loading, not aggregate results. This is not an application memory measurement or new cold/warm startup experiment. The important regression contract is zero object projection, not elapsed time.

## What the current checks establish

Normal existing current-schema Catalog and Preview startup each execute `PRAGMA quick_check;` once. They do NOT execute the more exhaustive `PRAGMA integrity_check;` on this path. Both current checks read across the database, so “quick” does not mean bounded readiness I/O. Accepted phase measurements were Catalog 53.47 seconds cold-ish / 2.64 warm, Previews 48.54 / 2.87, total process-to-usable 103.15 / 6.64. Cache effects explain the accepted difference; there is no daily-check policy.

SQLite quick_check detects many structural inconsistencies: malformed pages/records, ordering/allocation/freelist problems and applicable CHECK/NOT NULL violations. Unlike integrity_check, it omits UNIQUE verification and index/table-content consistency checks. Neither checks foreign-key consistency; that requires foreign_key_check. Neither establishes valid application JSON, timestamps, source fingerprints or authored intent. [SQLite check definitions](https://www.sqlite.org/pragma.html#pragma_quick_check).

Opening SQLite and reading identity/schema can detect a bad header, unreadable file or damaged pages encountered by those operations. WAL recovery reconciles committed transaction frames and interrupted transactional state; it does not certify every untouched database page. Successful schema/version reads establish compatibility, not structural integrity. [SQLite WAL recovery](https://www.sqlite.org/wal.html). Offline file damage, filesystem/hardware errors and incorrect external replacement remain possible after an orderly close. [SQLite corruption mechanisms](https://www.sqlite.org/howtocorrupt.html).

### Catalog: precious authored state

`CatalogDatabaseService.OpenExisting` opens read-only, quick-checks, validates application ID, version, migration history and Catalog identity, and only then admits normal use or the explicit migration path. Normal connections use WAL, synchronous FULL, foreign_keys ON and a busy timeout. FK enforcement protects new applicable writes; it does not retrospectively scan pre-existing relationships. Existing duplicate application of connection policy is small and unchanged.

The blocking scan provides early detection of the corruption classes above before ordinary authored mutations. It is neither a perfect semantic validator nor a guarantee against damage occurring later. Opening, preparing a representative SELECT, checking required objects and reading identity cannot provide the same coverage. No lighter pragma has been established as an equivalent substitute.

If skipped, a damaged page might remain untouched until a later collection/edit/export query. SQLite can return CORRUPT, NOTADB or an I/O error then, but detection is not guaranteed before other authored writes. Structurally valid but incorrect data may be acted on without a SQLite error. Current Catalog mutation lifecycle supports admission/drain; it does not centrally poison every connection and stop every future write on corruption. Existing UI exception handling is not a coordinated recovery latch. Therefore Policy B cannot claim fail-safe equivalence in the current architecture. Retain per-session blocking Catalog quick_check to preserve the accepted pre-use detection contract. This is a Lightflow safety decision, not a claim that every SQLite application must do this.

A future runtime corruption latch should stop new Catalog mutations, drain/cancel affected work, preserve originals and offer explicit recovery. That would improve containment but still would not retroactively undo writes made before latent damage was discovered. Never silently replace or rebuild Catalog.

### Previews: derived state with persistent retry semantics

`PreviewStoreService.EnsureInitialized` inspects existing storage read-only via `ValidateForMigration`: quick_check, application identity and schema compatibility. It then opens its WAL/NORMAL connection, migrates if necessary, and validates afterward (another quick_check only when migrated). Corrupt startup storage is rejected by the coordinator; Preview availability becomes false while Catalog can remain usable.

Today, rejection does not automatically quarantine and recreate the database. Maintenance requires an available provider, so existing Clear/Rebuild controls are not a complete corrupt-database recovery path. This capability must be implemented before calling a future deferred policy safe.

Missing artifacts and invalid metadata can fail lazily and regenerate through existing work identity/source checks. Some malformed domain fields can instead throw during record parsing despite a successful SQLite check. Scheduler error handling is not yet a universal Preview corruption latch. Metadata may affect presentation or derived decisions; separate files alone do not prove total application-level isolation. Source observation legitimately writes Catalog independently, so fault recovery must not interpret a Preview error as permission to alter Catalog/source state.

Derived storage may be quarantined and replaced after confirmed corruption, preserving Catalog and source media. On healthy restart, retained artifacts and #321 failure deadlines must remain intact. Never clear healthy retry state merely because startup was abnormal; that can restart failure loops. Use bounded, demand-driven regeneration, not a whole-Catalog rebuild.

## Clean-state evidence and proposed marker (design only)

There is no durable per-store clean-shutdown attestation. Catalog disposal clears pools; Preview disposal attempts a truncate checkpoint and catches failures. Neither records successful writer drain/checkpoint/close durably. WAL presence/absence, a PID, settings, job checkpoints and file timestamps cannot distinguish all requested states. Backup metadata identifies a snapshot and Catalog, not the health generation of the later live file. Current startup cannot reliably classify prior clean vs crash/power-loss termination.

The smallest defensible future marker is a per-store durable journal, not a boolean: version, store/file identity, schema/generation, session nonce, monotonically increasing sequence, transition reason, length/checksum. Bind it to a store-specific exclusive lease and physical file identity as well as logical identity; Preview currently lacks a unique store-generation identity, which must be supplied by this protocol. Restore/replacement invalidates the generation. A mismatch, missing marker, partial tail or unsupported format means uncertain. Never fall back to an older Clean record after a partial Dirty write.

Before any mutable open/recovery, migration, restore or writer admission, append Dirty and require durable flush acknowledgement. If that fails, no fast-path writes are authorized; fail closed for this protocol. On shutdown: stop admission, drain writers, finish/cancel jobs, complete database close/checkpoint with success propagated, then durably append Clean for that exact generation/session. No write may follow Clean. A crash/kill/failed close leaves Dirty; an interrupted journal write leaves uncertainty. Filesystem/device durability assumptions still apply, as with SQLite itself. An external replacement or offline bit flip can defeat assumptions without a process crash; a marker is evidence of lifecycle completion, not a page-health certificate.

Backup success is not Clean. Cancellation/failure that resumes the application leaves Dirty; skipping an optional backup does not prohibit a later genuinely clean shutdown. Restore/migration must record their transition before touching storage; their completion does not permit Clean while writers remain active. Current swallowed Preview checkpoint errors must become observable before this marker could be trusted. No marker has been added in this change.

## Exact proposed Policy C startup contract

Catalog always retains current read-only quick_check plus identity/schema/history gates before authored use. No asynchronous Catalog scan races normal writers.

Preview lightweight synchronous readiness means: open/read-only SQLite transaction successfully (including necessary WAL recovery); confirm expected application ID and PreviewStoreInfo identity; read exact supported user_version; prepare required read/write statement shapes and inspect required tables, columns and indexes; execute bounded reads of identity and a representative record; reject incompatible/malformed results. Apply and verify existing connection pragmas before write admission. These checks provide compatibility and touched-page readiness only. `foreign_keys=ON` is enforcement, not a scan; blanket foreign_key_check is not substituted for structural validation. No generic “lighter integrity” pragma is asserted to be equivalent.

| State | Catalog gate | Preview gate and next action |
| --- | --- | --- |
| 1. Proven-clean, current schema and matching generation | Existing unconditional quick_check and compatibility gates, then normal use. | Lightweight readiness, then enable normal demand/reuse. No unconditional global scan or census in background. Lazy faults invoke containment below. |
| 2. Abnormal or uncertain (including first adoption/missing marker) | Same blocking Catalog checks; open failure enters existing explicit recovery handling. | Lightweight classification only; withhold Preview work and run quick_check on a dedicated worker before activation, serialized with all Preview writers. Shell may expose honest Preview-unavailable placeholders with usable Catalog functions. Success preserves records/deadlines; corruption follows state 5. Busy/access/I/O errors do not by themselves authorize deletion. |
| 3. Migration required/incomplete | Existing preflight validation, mandatory protective backup, transactional migration/ledger and post-validation. No clean fast-path bypass. | Existing pre-migration check, transactional migration, version and post-migration validation before activation. Failure leaves unavailable and original evidence intact. No historical migration re-acceptance is implied. |
| 4. Restore/recovery | Invalidate marker/generation first. Preserve source/protective backup, candidate/staging validation, atomic publication and reopen/rollback contracts. Validate restored Catalog before use. | Invalidate attestation when binding changes; validate compatibility and affected derived state before reuse. Catalog restore is not permission to erase all Preview state without its existing identity rules. |
| 5. Corruption detected at startup or later | Refuse writes/use; preserve files and surface explicit recovery. Later detection needs the proposed central fault latch; it is not currently guaranteed. | Stop admission, cancel/drain Preview work, close handles, and quarantine only owned DB/WAL/SHM as a unit. Recreate a healthy store only under the approved recovery action; bounded lazy regeneration. Preserve Catalog, source files and reusable artifact files where safe. Failed quarantine means unavailable, never delete-and-hope. |

Deep Preview checks are triggered by uncertain/Dirty/mismatched marker, SQLite open/recovery structural anomaly, malformed persisted domain response, migration, restore/recovery generation transition, or explicit diagnostic request. Diagnose transient lock/permission/disk errors separately. Ordinary work-version changes trigger existing per-record invalidation/retry rules, not global corruption scans or retry clearing. No clock/day trigger. A check after activation must use an explicit consistent SQLite snapshot or the drained Preview writer gate; its result applies to that snapshot/generation, not to arbitrary later writes.

This proposal intentionally relaxes early detection for clean derived storage. It does not pretend a fast gate certifies every Preview page. Required containment/recovery and marker tests are architecture prerequisites, not features delivered here. The initial implementation can use the gate rather than introducing background snapshot lifecycle complexity.

## Backup, restore and migration relationship

Exit backup quiesces complete logical Catalog mutations, makes an online SQLite snapshot, fully validates the staged copy and identity/schema, flushes and publishes it. A successful snapshot is useful recovery evidence for that snapshot, not durable proof about all later live-file bytes. SQLite online backup provides a consistent snapshot under its API contract. [SQLite backup API](https://www.sqlite.org/backup.html).

When backup succeeds into exit, mutation admission stays closed. Cancellation/failure can reopen admission; backup skipped/disabled supplies no validation evidence. There is no mandatory live-file shutdown scan or durable clean record for every exit. Startup quick_check may inspect content already included in a validated backup, but it validates the live database being opened. It is not a redundant guarantee that can be removed solely because a backup exists. Normal startup enumerates backup history; it does not open/validate every backup or create a new mandatory backup.

Catalog migration retains stronger pre-migration integrity validation and mandatory backup, transactional schema/history changes and post-validation. Preview migration retains pre/post checks and its current retry-state migration. Restore retains candidate validation, protection of the current Catalog, staged validation/publication, reopen and rollback. These independent gates are not bypassed by Clean or by the proposed Preview fast path. No backup or migration policy changes are part of #340's implemented slice.

## Recommendation and expected impact

Choose C for the next architecture review. The shipped census change removes unsolicited roughly 30-second post-presentation object accounting and its multi-gigabyte materialization mechanism, but does not reduce the accepted Catalog/Preview blocking integrity phases. Focused checks establish query/object shape rather than a precise new application peak-memory promise.

If C is later approved and implemented, normal eligible startup retains the Catalog phase (accepted cold-ish 53.47 seconds) and removes the unconditional Preview scan (accepted cold-ish 48.54 seconds). Remaining identity/schema/readiness work still costs I/O, and cache interactions prevent subtracting phases to predict an exact total. Abnormal Preview startup still requires validation before Preview activation; Catalog protection, migration, restore and backup guarantees remain independent. No precise new startup time is claimed. Stop for architecture acceptance before implementing any integrity-policy change.
