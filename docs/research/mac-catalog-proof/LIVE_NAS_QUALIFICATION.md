## Upstream constraints and storage alternatives

[SQLite WAL](https://sqlite.org/wal.html) excludes ordinary WAL over a network filesystem because its shared-memory coordination is host-bound. Its documented EXCLUSIVE-before-first-access exception avoids shared memory for a guaranteed sole connection/process; it does not guarantee network sync/locking or make Lightflow’s many normal pooled connections and separate recovery readers safe. We did not force another VFS or exclusive-WAL topology to manufacture a pass.

[SQLite network guidance](https://sqlite.org/useovernet.html) warns that remote sync/locking reliability varies and early successful tests cannot establish safety. Rollback journaling can mitigate risks but remote SQLite deployments are not guaranteed/tested across all networks. [Locking documentation](https://sqlite.org/lockingv3.html) distinguishes Unix POSIX/advisory and Windows locks and depends on truthful filesystem locks/sync. [VFS guidance](https://sqlite.org/vfs.html) warns that incompatible locking implementations can miss one another. Measured file-control VFS name is `unix`; that name does not identify every internal filesystem-specific I/O/locking method. The exact causal I/O-method path behind WAL refusal was not traced.

[Atomic commit](https://sqlite.org/atomiccommit.html) depends on journal/database flush ordering, reliable journal invalidation and filesystem operations; a successful rename does not establish crash-atomic multi-file replacement. [Corruption guidance](https://sqlite.org/howtocorrupt.html) covers lost hot journals, broken locks and moving/unlinking active files. Neither ordinary fsync success nor FULL proves server power-loss persistence. Additional read-only connection observed fullfsync/checkpoint_fullfsync0; these are diagnostic-connection defaults, not a durability audit.

[Backup API](https://sqlite.org/c3ref/backup_finish.html) provides SQLite-consistent snapshots but can fail with IOERR/BUSY/LOCKED and still depends on source/destination I/O. Lightflow inspects source, uses BackupDatabase, finalizes staging in DELETE, validates identity/schema and renames before publishing success. NAS backing I/O cannot be made reliable just by that API. A future product must keep last known good snapshots, fail closed on disappearance, preserve journals and treat uncertain commit outcomes explicitly rather than blindly retrying.

| Future model | Correctness / recovery | Performance / complexity / portability | Disposition |
|---|---|---|---|
| Direct NAS DELETE/FULL, single owner | Removes WAL shared-memory dependency; still depends on compatible locks, remote flush ordering, reconnect/cache and durable replacement | Extra network round trips; readers/writers block; explicit mount detection, connection policy, ownership and recovery redesign | Credible bounded experiment, unqualified support |
| TRUNCATE/PERSIST rollback | Same critical lock/sync assumptions; journal retention/invalidating semantics differ | May reduce directory work; must qualify server-specific behavior and hot-journal recovery | Not measured; no safety shortcut |
| WAL with EXCLUSIVE/no shared-memory or custom VFS | Narrow documented primitive, not a network durability guarantee; conflicts with current multi-connection design | Requires much broader connection/lifecycle changes | Not recommended as a small fix |
| Local active WAL + centrally stored closed snapshots | Retains current tested local runtime; explicit checkout/return preserves one logical Catalog, but conflict/ownership and publication must be defined | Local queries/cache; explicit export/return UX; hashes/IDs/manifest travel independently of mount spelling | Recommended initial storage boundary pending owner decision |
| Service owns local SQLite on server | Moves network boundary to operations instead of SQLite filesystem I/O | New narrowly scoped service/protocol, operational burden; shared logical IDs preserved | Future alternative, not implemented |
| MEMORY/OFF journals | Cannot provide required durable recovery | Faster is irrelevant to authored-state safety | Reject for durable Catalog |

## Paths, Preview and ownership policy proposal

Retain existing case-sensitive/CI APFS and SMB observations; do not repeat them for ceremony. Initial recommendation: reject case-sensitive roots for first release, and fail closed on all roots for casefold collisions, Unicode aliases/duplicates, lossy trim/backslash/reserved names and unresolved symlink target containment. CI APFS/SMB alone is insufficient. Preserve exact stored display names; do not globally NFC/uppercase repair imported identities. Enrollment/remap plus per-operation guards must address races and unavailable sources; diagnostics preserve IDs/authored state without destructive repair. This rejection policy is proposed, not implemented/proved. General exact-name support requires a versioned per-root comparison/key migration and older-writer rejection, as detailed in PROPOSED_ROOT_IDENTITY_ARCHITECTURE.md.

CatalogId/AssetId/RootId and authored relationships are portable intent. Per-MachineId PhysicalPath is local resolution; observed volume/share/file identity is local evidence, not a global primary key. A SMB share rename/mount spelling change must be an explicit remap, not an identity rewrite. Discovery observations are rebuildable; descriptions/classifications/collections/rules/markers/ranges/LUT assignments are not. Existing schema already supports per-machine root remapping but its lossy keys/containment prevent general safe roots.

Preview remains machine-local even for a future central Catalog. Measured production Preview4 at the independent local root reopened with WAL/NORMAL synchronous1/5000ms/integrityok, same native SQLite. Its absolute cache/artifact paths, decoder/image-format compatibility and source observations are local/rebuildable; centralizing them adds network traffic/cache contention/corruption blast radius without preserving authored intent. Catalog and Preview were independently rooted; NAS Preview was not run. UNC-only detection is insufficient on Mac.

Recommend one active Lightflow owner per logical Catalog, no simultaneous writers and no automatic stale takeover. SQLite’s transaction locks do not prevent two applications interleaving valid authoring or establish cross-host application ownership. Future cross-platform ownership must identify canonical storage/aliases, enforce exclusivity before all access, distinguish process crash from disconnected-but-live owners, drain handles before replace, preserve recovery artifacts and fail closed on uncertain ownership. Current Windows instance/kernel32 file identity cannot serve as that Mac/shared-storage adapter. No distributed locking algorithm implemented or claimed.
