# Lightflow Studio: macOS compatibility decision gate

Research date: 2026-10-05. Research only; architecture proposal awaiting owner review.

## Decision

**Near-complete functional and workflow parity is plausible, but has not been demonstrated. Adopt a staged shared Avalonia desktop UI and neutral C# application/domain core, with narrow Windows and macOS adapters. Windows should eventually leave WPF after equivalent packaged acceptance. Keep WPF shipping during extraction and qualification.** Do not make the Player depend on a UI framework's generic media widget.

The one fallback is a permanent Windows WPF shell plus an Avalonia Mac shell over the same neutral services and presentation models. Use it if Windows migration cannot meet its regression budget or fastest Mac availability becomes the overriding priority. It saves the initial Windows UI migration but imposes enduring two-view implementation and acceptance work. Two completely native UIs are considered but not recommended for the one-feature/two-platform goal.

For Mac playback, recommend a directly controlled FFmpeg decoding backend with a Metal presentation adapter and CoreAudio output, preserving Lightflow's existing semantic coordinator. Qualify this difficult seam before committing to the port. Evaluate libmpv first as a bounded opportunity to avoid owning a full decoder/clock implementation; accept it only if a pinned, redistributable build passes the same exact-PTS, reverse-step, Color and capture contract. It is a candidate implementation of the selected architecture, not assumed parity. Retain Windows Flyleaf during transition. Shared decode across both OSes is a later optional consolidation, not a prerequisite that endangers current Windows playback.

## What is Windows-specific, and what can be shared

The application is net8.0-windows, WPF with WinForms enabled, Windows manifest/ICO, and one Windows app assembly containing UI and much reusable logic. Flyleaf's D3D11/DirectComposition pipeline, NAudio WaveOut, WIC images, HWND/DWM activation/chrome, COM recycle operations, Windows identity/ACL bridge setup, Explorer, and private-desktop packaging/test harness are platform implementations. Inno and win-x64 publishing are separate release concerns.

Lightflow.Actions already establishes a package-free neutral boundary: 23 semantic descriptors, 77 curated variants, typed arguments/results, target generations, single-flight/serialized execution, repeat policy and cancellable holds. Browser scope/query/selection and stable AssetIds, Catalog authoring, Smart query intent, Color LUT semantics, immutable Export materialization, metadata normalization and global Jobs admission are strong extraction seams. They are not all separate neutral assemblies today.

Portability estimate by responsibility: action contracts are already shared; durable domain intent and query/planning algorithms have high expected reuse; application orchestration has medium-to-high reuse after scheduler/dispatcher/path injection; UI views have low direct reuse under a new framework; media runtime/rendering has low direct reuse; platform services and packaging require explicit implementations. Most product rules can be shared, but this is not a defensible percentage of the whole application. The screen of 248 production C# files found 165 without direct scanned platform symbols and 83 with them. Absence of a symbol does not establish dependency closure or portability. See the dependency inventory and raw match evidence.

Proposed dependency direction: views and native adapters depend on neutral application ports; application depends on domain/contracts; domain references no WPF, Avalonia control, Apple type, OS key, device, or NLE-specific identity. SQLite implementation may be shared infrastructure with RID-native packaging, while platform file identity/recovery evidence remains behind ports. Enforce this through independent builds and forbidden-reference checks during future implementation.

## UI and framework conclusion

Avalonia is the strongest desktop fit for Lightflow's custom dark workbench, dense Browser, retained panels and XAML/C# skills. Core is MIT and commercial applications require no framework fee; professional tools and controls are separate licensing decisions. Current DataGrid documentation marks it deprecated, so the Details/grid spike must select a maintained free control or costed custom realization; do not assume paid TreeDataGrid is mandatory or automatically free. [Core license](https://github.com/AvaloniaUI/Avalonia/blob/main/licence.md), [tool distinctions](https://docs.avaloniaui.net/tools/faq), [DataGrid status](https://docs.avaloniaui.net/controls/data-display/structured-data/datagrid/).

Avalonia's Mac backend provides AppKit-facing integration and native NSView hosting; embedded native surfaces composite separately, so Player overlays, hit testing, clipping and fullscreen need explicit qualification. Ordinary managed builds can be produced on Windows; fuller macOS workload/native builds require a Mac. Framework capability does not establish Lightflow's performance. [Mac integration](https://docs.avaloniaui.net/docs/platform-specific-guides/macos), [native interop](https://docs.avaloniaui.net/docs/app-development/native-interop).

MAUI uses Mac Catalyst, not a direct AppKit desktop UI; its MIT framework is free, but Lightflow would own substantial desktop control/customization work. Uno's Apache-2.0 core and Skia desktop support are credible, but its documented macOS native-control hosting gap is a material Player integration risk. Shared rendered UI is plausible in both; neither makes WPF XAML/code-behind portable unchanged. See FRAMEWORK_COMPARISON.md for evidence, score weights and sensitivity.

Retain Lightflow's near-black canvas, neutral surfaces, orange action/focus vocabulary, text-plus-shape status, restrained panel geometry and PNG identity. Port design tokens and semantic vector geometry; replace Segoe UI Variable with an available Mac typeface with measured metrics and reflow. Audit remaining Segoe symbol-font glyphs rather than assuming Windows fonts can be bundled. Native titlebar, menu bar and file dialogs may differ intentionally. Do not add a light-theme product mode during this port: current design is intentionally dark-only.

## Player and audio: the largest gate

Observed: current Flyleaf fork 3.11.8-lightflow.1 depends on Windows rendering/native APIs; the [upstream architecture](https://github.com/SuRGeoNix/Flyleaf/wiki) is Windows/D3D. A cross-platform FFmpeg binding does not make Flyleaf portable. Preserve the fork's accepted timestamp/seek/Color fixes on Windows until a replacement has equivalent evidence.

MediaPlayback.cs contains FrameworkElement inside both presentation and backend signatures. Thus even the nominal backend contract cannot be extracted unchanged. Split semantic source/transport/frame operations from a presentation-surface lease owned by the shell. Keep one current source generation, bounded serialized operations, actual displayed-frame timestamp, capture ownership, and cancellation. A new renderer must not create a second Catalog/range/Player authority.

Exact frame behavior means advancing to the next decoded presentation timestamp, and reversing to its immediate predecessor; never estimate by nominal fps or poll the play clock. Use decoder timestamps plus time base, start offset and presentation order. Missing/discontinuous timestamps require explicit failure/diagnostic policy. FFmpeg's best_effort_timestamp is heuristic when source timing is missing, so a non-null value alone is insufficient to claim source-exact timing. [FFmpeg frame contract](https://www.ffmpeg.org/doxygen/9.0/structAVFrame.html).

Recommended backend responsibilities: demux/decode, bounded seek/reconstruction cache, explicit presented-frame acknowledgement, hardware/software capability selection, audio clock and drift handling. Metal handles textures, viewport and Color shader composition; CoreAudio consumes bounded PCM. Share target arbitration, range/loop decisions, rational cadence intent and commands. Do not expose COM/D3D or Apple handles in the domain.

Backend comparison:

| Backend | Strength | Lightflow-specific concern | Decision |
|---|---|---|---|
| Direct FFmpeg + Metal/CoreAudio | Access to decoded frames, broad codec coverage and control of Color/capture order | Large clock/buffering/GPU/lifetime engineering responsibility; reverse decode and hardware transfer must be proven | Selected control-oriented architecture, gate before commitment |
| libmpv | Mature playback/audio/hardware implementation, stepping and shader facilities | Reverse-step accuracy is conditional; render timing is not proof of source PTS; screenshot/shader order and native embedding require proof | First bounded qualification candidate |
| AVFoundation | Native Apple media/audio integration, sample timestamps via CoreMedia | AVPlayer stepping support varies by item; native decode coverage may differ from FFmpeg; reader+renderer still substantial work | Useful platform primitives, not sole parity baseline |
| LibVLC/LibVLCSharp | Mature cross-platform media, Mac NSView integration, LGPL runtime | NextFrame is conditional; exact reverse-step and custom full Color/capture pipeline are not established | Lower-ranked candidate |

The mpv manual explicitly documents limitations of seek-based stepping. Its default build is GPL; an LGPL build excludes GPL-only code and must also have compatible dependencies. LibVLCSharp's media-player API supports Mac native view ownership but does not document Lightflow-level reverse/PTS guarantees. [mpv behavior](https://mpv.io/manual/stable/), [mpv licensing](https://github.com/mpv-player/mpv/blob/master/Copyright), [LibVLC API](https://docs.videolan.me/libvlcsharp/api/LibVLCSharp.Shared.MediaPlayer.html), [Apple stepping](https://developer.apple.com/documentation/avfoundation/avplayeritem/canstepbackward?changes=_2_1_8), [CoreMedia timestamps](https://developer.apple.com/documentation/CoreMedia/CMSampleBuffer/presentationTimeStamp).

Current internal Flyleaf audio is disabled. A companion FFmpeg process produces 48-kHz stereo PCM into bounded NAudio WaveOut output; pause/seek/step/source changes stop it, resume restarts from the settled video timestamp, speed uses atempo. Mac must replace WinMM. Prefer one backend clock/output lifetime; if initially retaining companion FFmpeg PCM, replace only the sink with CoreAudio and prove drift, seek restart, latency and device change. Miniaudio is a free MIT-No-Attribution/public-domain alternative that includes CoreAudio, but is not automatic synchronization. [miniaudio](https://github.com/mackron/miniaudio).

Qualification must include forward/reverse steps near zero/EOF and across long GOPs, VFR/B frames/nonzero start offsets, rapid alternating input, paused retained frame, silent step, speed/loop boundaries, audio devices/sleep/wake, volume/mute, selected audio streams, ranges/markers/Subclips, camera→creative LUTs/Compare Original, source+authored rotation exactly once, zoom/pan, fullscreen without reopen, full-resolution capture and review. Golden expected PTS/pixels derive from fixtures, not screenshots alone. Display color profiles and GPU precision need measured tolerances rather than bit-identical cross-OS output promises.

## FFmpeg, Export, metadata and images

FFmpeg/ffprobe process orchestration, metadata parsing and immutable Export intent are largely reusable. Package pinned Mac executables and dylibs per RID with provenance/hashes and executable permissions; never depend on a user's Homebrew installation. Use ProcessStartInfo.ArgumentList rather than shell escaping. Retain cancellation, stderr/progress reading, source reservations and partial-output cleanup; replace Windows job/suspend behavior with explicit Mac process ownership.

Current production H.264/HEVC export is NVENC-only when capability probes succeed. CPU/AMF/QSV are currently NotImplemented; tests using CPU fixture encoders do not change shipped capability. Mac must map accepted intent to probed VideoToolbox H.264/HEVC capabilities and truthful settings, not copy NVENC flags. FFmpeg exposes those encoders and ProRes VideoToolbox, but codec/profile/device availability is a runtime property. ProRes expansion requires a product decision; it is not required merely because a Mac can encode it. [FFmpeg VideoToolbox definitions](https://www.ffmpeg.org/doxygen/8.1/videotoolboxenc_8c.html), [Apple VideoToolbox](https://developer.apple.com/documentation/videotoolbox?language=objc).

Keep source-relative trimming and inclusive UI Out→exclusive next-frame boundary, operation ordering, deinterlace/Color/rotation/scale, content-addressed LUT snapshot provenance, output naming/reservations, HEVC hvc1 and inherited-timecode handling. Probe a real tiny encode/decode result, not encoder-name presence. Export parity means equivalent accepted output intent and frame boundaries; bitstreams, speed and quality controls differ by hardware.

Current playback and export bundles have different pinned FFmpeg releases. Preserve that distinction until qualification allows consolidation. FFmpeg is LGPL2.1+ unless optional GPL components are enabled; nonfree combinations are not a redistribution shortcut. Package exact sources/build configuration and notices, and audit codec patent/commercial obligations separately from open-source fees. [FFmpeg legal/build guidance](https://ffmpeg.org/legal.html).

WIC is used by still-image metadata/thumbnail generation and WPF bitmap surfaces throughout previews, posters and captures. Split neutral decoded pixels/metadata from UI images. Recommend a shared SkiaSharp image/bitmap abstraction for common formats, with Windows WIC and Mac ImageIO adapters for native metadata/format gaps. Validate EXIF's eight orientations, embedded ICC, alpha/bit depth, multiframe policy, file-handle release and detached caching. SkiaSharp is MIT; its native dependencies still require an inventory. ImageSharp's current commercial-use thresholds make it unsuitable as an assumed unconditional free dependency. [SkiaSharp](https://github.com/mono/SkiaSharp), [ImageIO](https://developer.apple.com/documentation/imageio), [Six Labors terms](https://sixlabors.com/pricing/). JPEG XR/WDP and RAW coverage are gates, not claims; existing RAW placeholders do not imply an accepted RAW decoder.

## Same Catalog, different machine

**Expectation: the same logical Catalog can move between OSes after path/identity adapters and round-trip acceptance; the current Windows application is not safe to declare Mac-ready.** Schema 19's AssetId/RootId, descriptions, classifications, Collections/Smart intent, markers, ranges, Subclips and authored rotation/Color assignments are durable product state. Keep machine mapping IDs, resolved absolute paths, shortcuts/preferences/window state, NLE install credentials and unfinished machine-bound job execution separate. Previews are rebuildable derived state, not the portability contract.

Pinned Microsoft.Data.Sqlite 8.0.29 and all SQLitePCLRaw 2.1.13 packages resolve in the source lockfile. The native archive contains runtimes/osx-arm64/native/libe_sqlite3.dylib (1,696,624 bytes) and osx-x64 equivalent (1,724,472); Mach-O CPU types match arm64/x64 and both contain 3.53.3. Archive SHA256 is D07D13B4779123CFA56B3348B504D57A2AB6FC10C764FB6E2C9D787987E39201. This is static evidence only. Future Mac packaged verification must load the actual signed library, report version/compile options/schema/integrity and prove Catalog and Preview use one selected runtime. Do not silently use Apple's system SQLite or follow current upstream 3.x package changes during this research. [Pinned native package](https://www.nuget.org/packages/SQLitePCLRaw.lib.e_sqlite3/2.1.13), [Microsoft provider guidance](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/custom-versions).

MediaRoots.cs normalizes slash-separated relative paths but RelativePathKey uppercases them and containment uses OrdinalIgnoreCase. Other file/output/NLE identity paths also fold case. APFS supports both case-sensitive and case-insensitive volumes. A Mac root containing A.mov and a.mov cannot be imported safely under that key policy. Decide whether to reject ambiguous roots initially or introduce an accepted portable identity policy/migration; neither can be silently patched here. Include Unicode NFC/NFD, case-only rename, reserved Windows names, literal backslash on Unix, symlink escape, volume remount, SMB share mapping and cross-volume copy tests. [Apple volume formats](https://support.apple.com/en-gb/guide/disk-utility/dsku19ed921c/22.7/mac/26).

Move a quiescent Catalog through an application-created consistent backup, then verify and map roots on the destination. Do not raw-copy an open database or discard live WAL state. A portable database format does not make a concurrently used network Catalog safe. Keep Catalog local; media may be external/SMB. macOS permits unlink/rename of open files in ways Windows does not; recovery/exclusive ownership must prove all handles closed before replacement. StartupStoreEvidence's Windows volume/file-ID evidence needs a Mac file identity/durability adapter; never weaken clean-session certificates to timestamps alone. [SQLite file format](https://www.sqlite.org/fileformat2.html), [WAL](https://www.sqlite.org/wal.html), [corruption/backup conditions](https://www.sqlite.org/howtocorrupt.html).

Catalog Color assignment identity is portable intent, but the Catalog alone does not carry every configured .cube resource or immutable historical Export LUT object. Transfer/relink identical LUT content explicitly and retain hash verification; missing resources must surface unavailability without substituting Original. Unfinished jobs with absolute source/output paths and NLE destination journals are not automatically runnable after migration. Favorites are currently backlog #323, so the UI inventory records future portability work without adding a new first-Mac feature.

## Filesystem and Mac application services

Share file-operation intent, collision planning, job lifecycle, verification, Catalog mutation and no-destructive-fallback rules. Implement Finder reveal, native dialogs, file-URL clipboard/drag and drop, volume enumeration, native Trash, file identity, same-directory atomic replacement and per-volume path comparison behind services. FileSystemWatcher is a change hint: coalesce and reconcile with enumeration after event overflow/remount. Symlinks/aliases must not defeat managed-root containment. Never infer safe deletion from a Mac path's spelling.

Apple FileManager provides Trash operations; recoverable capability on external/network volumes remains a fixture gate. If Trash is unavailable, report unavailability; permanent deletion requires the existing explicit operation/confirmation. [Trash API](https://developer.apple.com/documentation/foundation/filemanager/trashitem%28at%3Aresultingitemurl%3A%29?changes=_1).

Mac shell must support application menu/About/Settings, Command-Q versus closing a window, Dock reopen, file-open events, native fullscreen Spaces, activation, multiple displays/Retina, accessibility and permission denial. Single-instance identity remains stable per user/product/profile before storage opens; choose AppKit activation plus user-scoped IPC/file-lock ownership and verify crash recovery. Do not mechanically reuse Windows named objects and user32 foreground activation. Native close semantics must explicitly preserve/cancel Jobs, warn about dirty Inspector/Settings work and flush state. Sleep/wake/device disappearance must invalidate unsafe media work and reconcile without authoring unintended Catalog changes. [App lifecycle surface](https://developer.apple.com/documentation/appkit/nsapplicationdelegate?changes=la), [Avalonia accessibility](https://docs.avaloniaui.net/docs/app-development/accessibility).

Proposed direct-distribution storage: resolve ~/Library/Application Support/<stable bundle ID> for Catalog default, preferences, shortcuts, workspace, machine mapping, journals and backups; ~/Library/Caches/<bundle ID> for rebuildable Previews; ~/Library/Logs/<bundle ID> for activity/diagnostics; OS temporary directory for disposable process/job files. User-chosen Catalog/backup/media destinations remain external after access checks. Do not write state into the .app bundle; --data-root continues to override all task/test state. Inspect backup/recovery location ownership before changing current layout. [Apple directory guidance](https://developer-mdn.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/MacOSXDirectories/MacOSXDirectories.html). Sandbox security-scoped bookmarks are machine/app-local grants, not portable Catalog paths. [Bookmark access](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox?language=objc).

## Distribution, costs, hardware and validation

Choose direct signed/notarized .app in a DMG (optional ZIP) first, Apple Silicon native first. Professional direct download requires Apple Developer Program at **US$99/year**, Developer ID, hardened runtime, notarization and stapling; no App Store listing is required. Local development needs no paid membership. Unsigned/unnotarized downloads can be shared but normally trigger Gatekeeper friction; Apple documents per-app Open Anyway after an attempted launch, and managed policy may prevent it. App Store uses the same annual membership plus review/sandbox/distribution requirements, with commissions only relevant to applicable paid transactions. See COST_MATRIX.md for six distinct paths, exact source dates and what is optional. [Apple membership](https://developer.apple.com/programs/), [current Gatekeeper behavior](https://support.apple.com/en-us/102445).

Sign every nested Mach-O/dylib/helper inside-out, then .app/container; notarize the final archive, staple a supported bundle/container and test a freshly quarantined download on a clean Mac. Validate .NET JIT entitlements minimally, loader-relative install names/rpaths, executable modes, SQLite/media assets and network-permission behavior. Avoid requiring disabled library validation without evidence. Runtime signing is distinct from App Sandbox, and notarization is distinct from App Store review. Updates should initially replace the whole signed bundle and preserve data; an automatic updater is separate signed supply-chain work. [Notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution?changes=_1_8_5), [workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow), [JIT entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-jit?changes=_3), [Store rules](https://developer.apple.com/app-store/review/guidelines/#software-requirements).

Minimum viable development/acceptance plan: an available Apple Silicon Mac with 16 GB RAM, SSD space for Xcode/SDKs plus disposable media and package output, a real display/audio device and maintained macOS matching a pinned supported Xcode/.NET toolchain. This is a proposed practical floor, not benchmarked app minimum. Ideally 24–32 GB RAM, 1 TB internal or fast external fixture SSD, two displays including Retina, a separate isolated test host/session and access to representative audio/removable/network/controller hardware. Retain a Windows NVENC acceptance machine. Do not buy Intel hardware until owner demand justifies x64 parity cost; if Intel is promised, physical Intel performance/media acceptance is mandatory, Rosetta or cross-publish alone is insufficient. [Apple toolchain host matrix](https://developer.apple.com/xcode/system-requirements). Hardware quotes depend on region/configuration; no purchase or exact model requirement is implied.

Windows can build neutral libraries and ordinary Avalonia managed Mac output; it cannot verify AppKit/Metal/CoreAudio or deliver final Apple-native toolchain/signing acceptance. Use a Mac for native adapters, final packaging/signing/notary and debugging/profiling. Set deployment floor only after intersecting .NET, UI/native dylibs, codec backend and promised Premiere/TourBox requirements. Current net8 support ends 2026-11-10; propose separately accepted .NET 10 LTS toolchain planning, not an unrequested TFM edit. [Microsoft support policy](https://dotnet.microsoft.com/en-us/platform/support/policy).

CI proposal: neutral/domain tests on Linux/Windows/Mac; Windows WPF/native tests through the existing private-desktop boundary; Avalonia headless control/layout tests; Mac native tests on isolated disposable GUI sessions/VMs or dedicated hosts; signed package smoke; media corpus/PTS/pixel/audio contracts; Catalog Windows→Mac→Windows round trips; real Premiere and physical controller scheduled acceptance. Preserve --data-root and bounded owned-process cleanup. macOS has no equivalent of CreateDesktop; do not automate in the owner's active GUI, switch sessions or synthesize global input there. Headless tests don't prove native rendering or focus. GUI VM GPU behavior must itself be qualified; physical performance and NLE/controller checks remain. [Headless limits](https://docs.avaloniaui.net/docs/testing/setting-up-the-headless-platform).

The repository is public, so standard GitHub-hosted Windows/macOS jobs are currently free, subject to service limits. Hosted Mac labels cover arm64 and Intel; choose explicit qualified labels, not a floating latest as support evidence. Private-repo billable standard Mac jobs currently cost $0.062/minute: 1,000 billable minutes = $62 before storage/taxes. ## Migration and development model

See PROPOSED_MAC_ROADMAP.md for staged children, dependencies, ranked spikes and release DoD. Sequence: decide budget/support/parity → prove Player and Catalog hazards → extract core while WPF ships → Mac adapters and shared UI vertical slice → complete Mac parity → separately accepted Windows view migration → packaged/public qualification. Do not wait for a complete UI rewrite to test media. Do not ship a partial shell as near-complete parity.

Proposed assemblies: retain Lightflow.Actions; add neutral Domain, Application and infrastructure/service libraries by dependency closure; keep Windows WPF shell/adapters; add shared Desktop UI and Mac/Windows entry points; isolate playback contracts, Windows Flyleaf, Mac FFmpeg/Metal/CoreAudio; separate packaging and native test heads. Avoid prematurely creating one project per small class or a generic plugin framework.

Future examples: a Browser filter adds one shared query/descriptor and regression fixtures plus one shared view; platform tests cover focus/virtualization. A Player review command adds one action/range policy and semantic suite, with a backend contract check for each renderer. A Settings/shortcut feature adds one preference/profile schema and conflict engine plus one shared editor; adapters supply OS gestures and lifecycle. Platform-specific capability exceptions require an issue decision and a row in the parity matrix. During two-shell transition, both view changes are tracked in the same feature's acceptance; no new domain rule lives in WPF or Mac code-behind.

## Parity ceiling, largest risks and open decisions

Target near-complete semantic/workflow parity with common visual identity and intentional native chrome/input conventions. Do not promise identical fonts, windows, codec bitstreams, GPU performance, color-managed monitor output, third-party NLE APIs or vendor transports. The first public Mac release must either satisfy each required capability row or disclose an owner-approved exception; “framework runs” is not the gate.

Largest unresolved risks: exact Player semantics and GPU integration; case/Unicode Catalog identity; migration of mature Windows UI without regressions; image/Color consistency; signed native dependency packaging; actual NLE/controller behavior. Effort is substantial and cannot be responsibly reduced to a calendar estimate without spikes. There is no mandatory core framework/runtime license fee in the proposed architecture; Mac access, engineering/QA and the $99/year professional distribution account are unavoidable resource needs.

Owner decisions before implementation: approve eventual Windows Avalonia migration or fastest-Mac fallback; choose first Mac audience/OS floor and Apple Silicon-only versus Intel; accept the Player proof budget and failure exit; decide initial case-sensitive-root policy; confirm direct distribution and enrollment identity; define media corpus/performance/color tolerances and required image formats; decide NLE/controller release gates without changing their current scopes. No request for approval is embedded here: these are the next architecture review agenda.
